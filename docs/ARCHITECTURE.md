# Architecture

How the mod reads a save, keeps every player up to date and draws the overlay. For the guide data format see [DATA_FORMAT.md](DATA_FORMAT.md).

## Big picture

```
            SERVER (Osiris)                                   CLIENT (each player)
 +------------------------------------+            +-------------------------------------+
 | Osiris events                      |            | Hotkey (F7 / MCM keybinding)        |
 |  FlagSet / FlagCleared             |            |   -> UI.Toggle                      |
 |  QuestUpdateUnlocked               |   Hello    |                                     |
 |  ApprovalRatingChanged     <-------+------------+ StateClient                         |
 |  Died / party / level              |            |   Hello {open, want}                |
 |        |  (watched only)           |  Override  |   Override {id, value}              |
 |        v                           <------------+                                     |
 | StateServer (400 ms debounce)      |            |                                     |
 |   per player: avatar -> snapshot   |   State    |                                     |
 |   FlagEvaluator.BuildSnapshot  ----+----------->+ OverlayWindow (in-place refresh)    |
 |   diff -> notifications        ----+----------->+ Toasts                              |
 |   check-offs in a mod variable     |   Toast    | Settings (settings.json <-> MCM)    |
 +------------------------------------+            +-------------------------------------+
```

BG3SE runs a separate Lua state for the server and for every client, even in single player. Osiris (flags, journal, databases, approval) only exists on the server, so the server evaluates everything and clients only draw.

## Load order

Both bootstraps load `Shared/Core.lua`, `Data/Flags.lua`, `Data/CompanionGuides.lua` (which loads `Data/Companions/*.lua`) and `Tracker/FlagEvaluator.lua`. The server adds `Tracker/StateServer.lua`. The client adds `Client/*`, `UI/*`. All files share the mod environment (`Mods.CompanionRoadmap`) through the global table `CR`.

`Ext.Require` must only be called while bootstrapping: it resolves paths against the mod that is currently loading.

## Data layer

- `Data/CompanionGuides.lua` defines the condition constructors (`CR.Cond`), the companion registry (`CR.Guides`), progress markers and deadlines. After loading it builds the **watched set**: every flag GUID and quest id referenced anywhere.
- `Data/Flags.lua` is generated by `tools/build_data.py` from the game's flag definitions and journal. It maps names to `{ guid, usage }` and quest ids to journal titles.

## Evaluation (server)

`CR.Eval.BuildSnapshot(avatar, overrides)` creates a context for one avatar. Every Osiris probe goes through `pcall`, and its result is cached for that snapshot:

| Probe | Osiris call |
|---|---|
| flag | `GetFlag(guid, NULL / avatar / companion)` depending on the condition and the flag's usage bits |
| journal | `QuestUpdateIsUnlocked(NULL, quest, step)` (also the `ORI_Avatar_` variant) |
| relationship | romance flags plus `DB_ORI_Dating` / `DB_ORI_Partnered` |
| recruited | `GLO_Origin_PartOfTheTeam_<Name>` or `DB_PartOfTheTeam` |
| dead | `IsDead`, `DB_PermaDefeated` |
| knocked out | `DB_KnockedOut`, `DB_ORI_Minthara_RemoveKnockedOutLater`, `HasActiveStatus(KNOCKED_OUT*)` |
| approval | `GetApprovalRating(companion, avatar)` |
| progress | `DB_CurrentLevel` / `GetRegion`, `VISITEDREGION_*` and the marker flags |

The status rules are documented in [DATA_FORMAT.md](DATA_FORMAT.md#how-a-status-is-decided).

### Snapshot (server -> client)

```lua
{
  p = 1, v = "1.0.0", ready = true,
  avatar = "<guid>", level = "SCL_Main_A", region = "Shadow-Cursed Lands", act = 2,
  markers = { act1Locked = false, colony = false, ... },
  steps = { SH_A1_PARTY = { "D", 2 }, MIN_A1_KO = { "M", -1 }, ... },  -- status, evidence index
  comps = { Shadowheart = { rec = true, a = 47, rel = "dating", dead = false, lost = false,
                            cnt = { nightsong = { bits = {1,0,1,0,0,0}, reached = false } } }, ... },
  ov = { SH_A1_IDOL = true },                                           -- manual check-offs
}
```

The evidence index points into the step's `done` list (positive) or `fail` list (negative), so the client can say *why* a step has its status without the server sending text.

## Synchronisation

- Channels are created with `Ext.Net.CreateChannel(ModuleUUID, ...)` on both sides: `Hello`, `Override` (client -> server), `State`, `Toast` (server -> client).
- A client sends `Hello` when the game reaches the `Running` state and whenever the window opens or closes. The server remembers each peer and whether its window is open.
- Osiris listeners mark the state dirty only for watched flags/quests and tracked companions. A 400 ms debounce coalesces bursts (a single dialogue can set dozens of flags).
- On flush the server rebuilds each peer's snapshot. Open windows get the snapshot. Every peer gets notifications for steps that changed to DONE (or to MISSED, if critical and not optional).
- After `LevelGameplayStarted` (save loaded, region change) the next evaluation is a silent baseline, so loading a save never floods the player with notifications.

### Multiplayer

The server maps a peer to its avatar with `GetReservedUserID` on `DB_Avatars` (falling back to `GetCurrentCharacter`, then the host). Approval and romance are therefore per player; journal progress and check-offs are shared.

## Persistence

| What | Where | Scope |
|---|---|---|
| Manual check-offs | mod variable `Overrides` (`Ext.Vars.RegisterModVariable`, persistent) | per savegame |
| Settings, hotkey, last companion | `Script Extender/CompanionRoadmap/settings.json` (`Ext.IO`) | per user |
| Settings (when MCM is installed) | mirrored to MCM; changes in either place sync both ways | per MCM profile |
| Window size/position | ImGui's own `imgui.ini` (sizes use `FirstUseEver`) | per user |

## UI

- The main window is created lazily on first open and never rebuilt. A companion page is built when selected; later refreshes only change labels, colours and visibility, so scroll position, expanded steps and the selected tab survive live updates.
- Interactive elements whose label changes use ImGui's `Label###stableId` syntax so their state is kept.
- Notices are queued on the server while the player is in a conversation (`DB_DialogPlayers`) and delivered when it ends.
- Journal text is never stored: `Data/Flags.lua` carries localisation handles and the client resolves them with `Ext.Loca.GetTranslatedString`, then replaces typographic characters the font cannot draw.
- The SE IMGUI font covers only ASCII + Latin-1. All UI text is validated for that; the only ornaments are Latin-1 (middle dot, right guillemet, multiplication sign).
- Top-level window sizes are absolute pixels (SE applies `SetSize` before a window's `Scaling`), so the first-run size is derived from `Ext.IMGUI.GetViewportSize()`. Inner elements use `Scaling = "Scaled"`.
- Look and feel (`UI/Theme.lua`): a near-black translucent window with a hairline bronze border, parchment text, gold headings, and colour reserved for meaning (next, done, missed, romance, deadlines).
- Fonts: SE registers Quadraat Regular at six sizes (`Tiny` 24 to `Big` 44). On first open the theme also loads the game's Demibold and Italic cuts with `Ext.IMGUI.LoadFont` under `CompanionRoadmap_*` names; if that fails the built-in sizes are used.
- SE scales its base style by viewport height / 1610 but pushes per-element style values unscaled, so the theme multiplies its padding and spacing by the same factor.
- Steps are rows of a two-column table (status | expandable step). The status text has a hover tooltip; the NEXT row gets a faint background band by pushing `TableRowBg` on that row only.
- Tabs are switched in code with the `SetSelected` flag, which is cleared again after 300 ms; otherwise the tab would stay forced.

## Portraits

`Public/CompanionRoadmap/Content/UI/[PAK]_UI/_merged.lsx` declares one texture resource per companion. Each resource only points at a Photo Mode sticker inside the game's own `Game.pak`, so the mod ships no art. `pack.ps1` converts the file to `.lsf`. `UI/Theme.lua` (`T.Portraits`) maps companions to the resource ids and `AddImage` draws them. A texture that fails to load draws nothing, so pictures always sit in their own table cell and never anchor the layout. `build_data.py` checks that the ids match and, with the game cache, that every referenced sticker exists.

## Report file

`!roadmap report` and *Options > Create a report file* make the server write `Script Extender/CompanionRoadmap/report.json`: the snapshot, every watched flag and journal step that is set (probed on every target the flag allows), the raw per-companion facts (dead, permanently defeated, in the team, knocked out, approval, dating, partnered) and the camp scheduler tables. It holds game identifiers only. `tools/test_harness.py` can rebuild a world from a report (`replay_report`), which turns bug reports into regression tests: put the file in `tests/fixtures/` and optionally add an `"expect": { "STEP_ID": "D" }` object.

## Hotkey

With MCM: the `toggle_roadmap` keybinding (`MCM.Keybinding.SetKeyDownCallback`) and the `open_roadmap` event button. Without MCM: a raw `Ext.Events.KeyInput` handler using the saved hotkey (default F7, rebindable by capturing the next key press). F8 is avoided because it is BG3's Quickload.

## Script Extender APIs used

`Ext.Net.CreateChannel` (v22+), `Ext.IMGUI` (windows, child windows, tab bars, trees, tables, tooltips, selectables, combos, progress bars, `LoadFont`), `Ext.Vars.RegisterModVariable`, `Ext.Osiris.RegisterListener`, `Ext.Timer.WaitForRealtime`, `Ext.IO.LoadFile/SaveFile`, `Ext.Events` (`SessionLoaded`, `GameStateChanged`, `KeyInput`, `ResetCompleted`), `Ext.RegisterConsoleCommand`. `Config.json` requires v25.

## Testing

`tools/test_harness.py` loads the real bootstraps into two independent Lua 5.4 states (via `lupa`) on top of `tools/mock_se.lua`:

- The IMGUI mock is generated from BG3SE's property map (`GameDefinitions/PropertyMaps/IMGUI.inl`). Unknown element types, properties, colour slots, style variables or conditions, unknown fonts, duplicate interactive ids, too many table cells, access to destroyed elements and non-Latin-1 text all raise errors. Every such error is also recorded, so a test fails even when the mod's own `pcall` swallowed it.
- A fake Osiris world provides flags, journal steps, databases and approval; messages travel between the states as JSON, with a simulated clock for timers.
- Scenarios cover boot, live updates and notifications, every UI interaction, the window layout (fonts, act sections, next-step highlight, warning links, filters), the Act 1 lock-out, Minthara's knockout and dependencies, origin characters, console commands and MCM integration.

The harness cannot prove rendering or real Osiris behaviour: changes that touch either should also be tried in game.
